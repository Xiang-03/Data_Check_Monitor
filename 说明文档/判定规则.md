# 判定规则

> 引用约定：`判定.py` 指 `_公共/监控内核/判定.py`，`自测_判定.py` 指 `_公共/监控内核/自测_判定.py`，`数据.py` 指 `_公共/监控内核/数据.py`，`消息.py` 指 `_公共/监控内核/消息.py`，`基础.py` 指 `_公共/监控内核/基础.py`；`每日对账.py` 指 `_公共/业务/每日对账.py`，`项目配置.py` 指 `_公共/业务/项目配置.py`；`模板/项目配置.ini` 就是模板目录下那份。文中的行号都是当前代码的真实行号。
>
> 判定只有一份实现：`判定.judge()`（`判定.py:160`）。业务层把原始信号递进来，不自己算“采集中”，也不自己算容差（`判定.py:25-30`）。

## 1. 一句话：输入与输出

`judge()` 的输入是**平台消耗、库内消耗、两个日期、若干原始信号和阈值**；输出是一个二元组 `(状态, 差额)`，差额 = 平台消耗 − 库内消耗（`判定.py:164`、`判定.py:192`）。

| 输入 | 含义 | 证据 |
|---|---|---|
| `plat` | 平台消耗（元）；`None` 表示平台这天没有记录 | `判定.py:167`、`判定.py:181-182` |
| `db` | 库内消耗（元），调用方传入标准投 + 简单投 | `判定.py:168`、`每日对账.py:404-405` |
| `day` / `today` | 统计日期 / 运行日，决定是否 T+0 | `判定.py:169-170`、`判定.py:196` |
| `stale` | 平台值是否取于该日结束之前（半成品） | `判定.py:171`、`每日对账.py:409-414` |
| `n_acc` / `base` / `fresh` / `ra_active` | 账户数、近 7 日账户中位数、最近是否仍入库、导出时 RPA 是否在重灌 | `判定.py:172-175` |
| `tol_abs` / `tol_rel` 等 | 容差和采集中阈值，全部由调用方从配置传入 | `判定.py:176`、`判定.py:162-163` |

差额只有在能算出平台值和库内值时才有意义：`plat is None` 时直接返回 `(待取数, None)`（`判定.py:181-182`）；其余状态都带 `p - d`。正差额表示平台大于库内（少采），负差额表示平台小于库内（多采/回刷）（`每日对账.py:490`）。

## 2. 八种状态核心表

状态名就是代码里的字面量（`判定.py:36-43`）。“终态结论”只指能作为本次运行结论、进入 `PASS n · 报警 m` 分母的状态；其余都是本次弃权，重跑会重新判（`判定.py:47-52`、`每日对账.py:451`）。

| 状态 | 触发条件 | 差额 | 是终态结论 | 人能做什么 |
|---|---|---|---|---|
| `待取数` | `plat is None`，平台这天没有记录（`判定.py:181-182`） | `None` | 否 | 调用方通常直接跳过、不产生行（`每日对账.py:401-403`）；先确认平台是否真无记录，应有则查取数 |
| `进行中` | `day >= today`，即 T+0 当天（`判定.py:194-197`） | `p-d`，仅展示 | 否 | 等次日数据收盘后再判；当天差额不要看 |
| `平台陈旧` | `stale=True`；调用方按 `fetched_at` 的日期 `<=` 统计日期判定（`判定.py:199-203`、`每日对账.py:413-414`） | `p-d`，不可当少采 | 否 | 修好取数后重跑；这批差额不能作为结论（`每日对账.py:486`） |
| `库内采集中` | `p>0` 且 `abs(p-d)>t`，且 `ra_active` 或 `collecting()` 为真（`判定.py:211-214`） | `p-d`，中间态 | 否 | 等 RPA 采完再跑；不要当少采（`每日对账.py:475`、`消息.py:135-143`） |
| `库内未导` | `p>0` 且 `d==0`，且没有先命中“采集中”（`判定.py:216-219`） | `p`（因为 `d=0`） | 否 | 先跑库内导出或补导，再重跑（`每日对账.py:502-503`） |
| `无消耗` | `p==0` 且 `d==0`（`判定.py:221-223`） | `0.00` | 否（弃权，不计数） | 核对确属双方停投即可，不计入通过率 |
| `通过` | 未命中前面分支，且 `abs(p-d)<=t`（`判定.py:225-226`） | `p-d`，在容差内 | 是 | 无需动作 |
| `报警` | 未命中前面分支，且 `abs(p-d)>t`（`判定.py:225-226`） | `p-d`，可正可负 | 是 | 按明细排查；`python 排查.py <日期>` 定位到账户/日期（`每日对账.py:499`） |

## 3. 判定优先级：顺序就是语义

`judge()` 从上到下 return，顺序不能调（`判定.py:31`、`判定.py:194-226`）。

1. **`待取数` 最前**：没有平台值就既没有分母也没有差额，后面的容差、采集中都无从谈起，所以先于所有金额判断（`判定.py:181-182`）。
2. **`进行中` 排在 `平台陈旧` 前面**：T+0 当天取数本来就只能在日末前抓，`fetched_at` 的日期必然等于当天；如果先判 `stale`，每天都会被误报成“平台陈旧”。所以当天数据先拦掉，后面所有判断都无意义（`判定.py:194-195`）。
3. **`平台陈旧` 排在 `库内采集中` 前面**：平台值是半成品时，分母本身就是错的。此时哪怕库内确实没采完、哪怕 `ra_active=True`，也不能把“取数失败”记到 RPA 头上；所以 stale 先返回（`判定.py:199-203`、`自测_判定.py:84-85`）。2026-11-13 的 B 路取数失败就是拿前一天 17:02 的快照去比全天库内数，凭空报出大额假警（`判定.py:200-201`）。
4. **`库内采集中` 排在 `库内未导` 前面**：`d==0` 既可能是“RPA 还没写到”，也可能是真的没导。对老店，`n_acc=0` 会先命中“账户数偏少”，此时判“采集中”比判“未导”更准确；只有（没有基准、账户数不偏少，或 `n_acc` 未知）且 `fresh=False`、`ra_active=False` 时，才会落到 `库内未导`（`判定.py:211-219`、`自测_判定.py:89`）。
5. **`库内未导` 排在 `无消耗` 前面**：先确保 `p>0,d==0` 被识别成“平台有数、库里没有”，而不是继续落到后面的通用分支（`判定.py:216-219`）。
6. **`无消耗` 只处理双方都 0**：`p==0 and d==0` 才成立，和“平台有数、库内 0”是两件事（`判定.py:221-223`）。
7. **最后才是 `通过` / `报警`**：走到这里说明没有命中前面那些弃权态，金额比较可以下结论，才用容差判通过或报警（`判定.py:225-226`）。

### 3.1 四个容易问的“为什么”

- **为什么 T+0 必须排在 `平台陈旧` 前**：见上第 2 条；`fetched_at` 在 T+0 只可能是当天，先判 stale 会把每一天都变成“平台陈旧”（`判定.py:194-195`）。
- **为什么 `库内采集中` 排在 `库内未导` 前**：`d==0` 是采集中的一种极端形态，先让“RPA 还没采完”解释它，避免把正常写入过程报成“库没导”（`判定.py:211-219`、`自测_判定.py:89`）。
- **为什么 `ra_active` 只在金额已超容差时才生效**：`ra_active` 只加在 `abs(diff) > t` 的分支里；已经配平的日子不管 RPA 在不在跑都该算通过，否则 RPA 一跑全月都变“采集中”，真报警会被淹掉（`判定.py:178-179`、`判定.py:207-214`、`自测_判定.py:95`）。
- **为什么 `p>0` 是采集中判定的硬前提**：平台是 0、库内却有数，属于多采/回刷，不能因为 RPA 在跑就放过；`collecting()` 自己也会在 `p <= 0` 时返回 `False`（`判定.py:209-210`、`判定.py:150-151`）。

## 4. 容差公式

```
t = max(abs_tol, |平台消耗| × rel_tol)
```

代码就是 `max(float(tol_abs), abs(p) * float(tol_rel))`（`判定.py:117-127`）。默认 `abs_tol=10`、`rel_tol=0.0001`，来自配置（`模板/项目配置.ini:49-53`、`项目配置.py:183-184`）。

- **绝对分量 `abs_tol`**：给小金额兜底。真实尾差通常只是 `ROUND(SUM(cost),2)` 的取整误差，金额很小；没有绝对下限，几元的日子会被判成报警（`每日对账.py:55`、`判定.py:120-121`）。
- **相对分量 `|平台| × rel_tol`**：让阈值跟着量级走。一天几十万时，固定 10 元形同不存在；相对项会把阈值抬到与业务规模相称的水平（`判定.py:120-121`）。

| 平台消耗 | 绝对项 | 相对项 | 实际容差 `t` |
|---:|---:|---:|---:|
| 80,000 | 10 | 8 | 10 |
| 600,000 | 10 | 60 | 60 |

判断只用 `abs(diff) <= t`：等于容差算通过，超过才算报警（`判定.py:225-226`）。所以平台 600,000、库内 599,940（差 60）是通过；库内 599,930（差 70）才是报警（`自测_判定.py:108-113`）。

## 5. 采集中判定：85% 是前提，两个信号是触发器

`collecting()` 的顺序是（`判定.py:130-157`）：

```
p<=0                          -> False
d >= p × acc_fill(0.85)       -> False     # 金额已基本采齐，不许再判采集中
否则：账户数偏少 或 最近仍入库  -> True
```

- **85% 前提**：金额采集率已经达到平台值的 85%，就直接认定“不是采集中”，不管账户数多低、最近有没有入库（`判定.py:152-153`）。
- **信号一“账户数偏少”**：`base` 存在、`base >= acc_base(5)`、`n_acc` 已知，且 `n_acc < base × acc_ratio(0.7)`（`判定.py:154-156`）。`base` 是 `day` 之前最近 7 天账户数的中位数，不含当天（`数据.py:52-65`）；中位数比均值抗噪，新增一批账户不会把基准拉高。
- **信号二“最近仍入库”**：`fresh=True`，调用方用入库时间表判断最近 `ingest_fresh_min` 分钟内还有写入（`判定.py:157`、`每日对账.py:421-423`）。
- **`n_acc=None` 不等于 0**：`None` 表示“账户数不知道”，不参与账户数判断，只能靠 `fresh` 触发；`0` 才算真的一个都没到（`判定.py:142-143`）。
- **`n_acc` 只统计标准投**：简单投账户太少，用它判“采集中”噪声太大（`每日对账.py:118-123`）。

**为什么 85% 这个前提不能去掉**：2026-11-09 有店铺真实停投，账户数明显下降，但金额分毫不差。只看账户数会把它误判成“还在采”，从而放过真实停投；只看金额又分不清“真少采”和“还没采完”。所以必须先看金额采集率，再用账户数/入库信号区分（`判定.py:138-140`、`自测_判定.py:75-80`）。反过来说，金额率 90%、账户数再低也判报警，不判采集中（`自测_判定.py:98`）。

`ra_active` 是另一条触发器：导出时刻距库内最后写入小于 `ra_active_min`（默认 10 分钟）时，整库都在删了重灌，任何差额都不可信（`每日对账.py:382-386`、`模板/项目配置.ini:66-67`）。它同样受 `p>0` 和“金额已超容差”两道限制（`判定.py:209-214`）。

## 6. 平台陈旧的定义

判定口径只有一句：**`fetched_at` 的日期 `<=` 统计日期，就不可信**（`每日对账.py:413-414`）。取数记录必须在该日结束之后抓取；当天抓到的平台值最多只是半成品。`fetched_at` 缺失也按陈旧处理（`when is None`，`每日对账.py:414`）。

调用方先把 `stale` 算好再传进来，`judge()` 只认这个布尔值（`判定.py:171`、`判定.py:199-203`）。`parse_ts()` 只给日期时也会解析成当天 00:00，因此同样会命中 `<=`（`基础.py:42-54`）。命中后 `judge()` 直接返回 `平台陈旧`，不会再去比金额，也不会判采集中（`自测_判定.py:84-85`）。消息里会明确写“这天的平台值是当天日末前抓的半成品，不算少采”，并提示修好取数后重跑（`消息.py:125-133`）。

## 7. 只有 `通过` / `报警` 是终态

`JUDGEABLE` 只包含 `通过`、`报警`（`判定.py:47-48`）；`NOT_COUNTED` 包含其余 6 态（`判定.py:50-52`）。`每日对账.py` 的 `judged` 也只加 `PASS` 和 `报警` 两项（`每日对账.py:451`）。

这条不是文字游戏：如果把 `库内未导` 算进“通过”，就会出现“库没导却全绿”。所以当 `judged == 0` 时，脚本不报“全部通过”，而是打印“本次没有任何可判定的日期”，并返回退出码 4（`每日对账.py:500-503`、`每日对账.py:551-552`）。

其余 6 态都是**本次运行的弃权/暂态**：`进行中` 等收盘、`平台陈旧` 等重取、`库内采集中` 等 RPA、`库内未导` 等导出、`待取数` 等平台记录、`无消耗` 只是不计数。`judge()` 是纯函数，不存状态；重跑时按新数据重新判（`判定.py:29-30`）。`通过`/`报警` 是本次运行的终态结论，但重跑仍会按新数据重算——它们只是“能对外作为结论”的那两种。

| # | 输入（假数） | 计算 | 结果 | 为什么 |
