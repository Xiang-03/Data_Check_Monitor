## 各份文档管什么

| 文档 | 内容 | 什么时候会过时 |
|---|---|---|
| **架构说明** | 三层结构、一次运行的数据流、分发模型（版本戳 + 三态冲突）、内核 14 模块职责、5 条不能破的不变量、目录约定 | 分层或分发机制变了才需要改 |

| **换平台改造清单** | 适配层契约（文件名/函数/CSV 列名）、9 处必须改的硬编码、8 步改造流程、验收清单、踩过的坑 | 平台抽象做了大改就要重写 |

## 共同约定

- **行号引用**：文中 `文件:行号` 都基于当时的代码。改过代码后行号会漂，**按函数名/报错文案搜更可靠**。
- **示例数据**：所有金额、店铺、组织码都是假的（`示例店铺A` / `123456` / `db.example.invalid`）。
- **不做的事**：不写真实客户名，不写真实 webhook key，不复制客户的事件记录进文档。
- **代码是唯一真相**：文档和代码冲突时，以代码为准，然后回来修文档。

## 文档改动守则

改公共代码时，顺手检查这几份：

| 改了…… | 要同步 |
|---|---|
| `判定.py` 的状态或阈值逻辑 | 判定规则 |
| 退出码、失败分支 | 运行与故障 |
| 新增/改名 ini 键 | 配置参考 + `模板/*.ini` 的注释 |
| 分层、分发机制 | 架构说明 |
| 适配层契约或硬编码位置 | 换平台改造清单 |
| 新增一个仓库级脚本 | `README.md` 的结构表 + 本索引 |

> 文档不是产物，是护栏的一部分：写错的行号会让人照着错的地方找，比没有文档更糟。
