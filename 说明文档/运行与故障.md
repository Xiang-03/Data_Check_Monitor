# 运行与故障

> 引用约定：`自动对账.py` 指 `_公共/业务/自动对账.py`，`每日对账.py` 指 `_公共/业务/每日对账.py`，`子流程.py` / `日志.py` / `通知.py` / `消息.py` / `基础.py` 均指 `_公共/监控内核/` 下同名文件；`心跳检查.py` 是项目根下那份；`项目配置.ini` 指 `模板/项目配置.ini`，`架构说明.md` 指 `说明文档/架构说明.md`。未单列的模块按所在层理解：`平台取数.py` / `凭证刷新.py` / `库内导出.py` 在 `_公共/平台/小红书/聚光/`，`写入日监控.py` 在 `_公共/业务/`，`路径.py` / `登录态.py` / `判定.py` 在 `_公共/监控内核/`。所有命令都在项目根（`数据监控/`）执行。
>
> 一条总原则：**正常对账链里只有 `自动对账.py` 会发消息**，`每日对账.py` 只打印；`心跳检查.py` 是另一条独立告警。通知靠正则解析 `每日对账.py` 的输出，改打印格式会静默打断推送（`架构说明.md:71-76`）。

## 1. 一次自动对账的时序

计划任务（本项目以 15:30 为例）调 `pythonw.exe 自动对账.py --always-notify`，起始目录是项目根；勾“错过后尽快启动”、不勾“唤醒计算机”（`接新客户一页清单.md:143-149`）。`--always-notify` 的含义是 rc=0 也推一条（`自动对账.py:262`）。

| # | 调用（文件:函数） | 做什么 | 关键证据 |
|---|---|---|---|
| 1 | 计划任务 → `自动对账.py:main` | 读配置、记开始时间、创建日志、`install_tee` 接管 stdout/stderr | `自动对账.py:131-134`、`日志.py:27-40`、`日志.py:66-68` |
| 2 | `自动对账.py:main` → `基础.in_window` | 不在 `[运行时段] window` 内直接跳过：不取数、不推送、rc=0 | `自动对账.py:176-184`、`基础.py:58-80` |
| 3 | `自动对账.py:preflight` → `基础.preflight` | 查依赖和关键文件；缺一项 rc=2，后面不再跑 | `自动对账.py:101-103`、`自动对账.py:186-191` |
| 4 | `自动对账.py:ensure_browsers` → `启动取数浏览器.ensure_all` | 复用已开窗口，或起无头浏览器；失败 rc=9 | `自动对账.py:107-110`、`自动对账.py:193-213` |
| 5 | `自动对账.py:run_reconcile` → `子流程.run_reconcile` → `子流程.run_script` | 起子进程跑 `每日对账.py`，逐行打印并收集完整输出；设 UTF-8 管道编码 | `自动对账.py:215-220`、`子流程.py:20-43` |
| 6 | `每日对账.py:main` 的 5 个阶段 | 见下表；返回退出码和全部文本 | `每日对账.py:163-557` |
| 7 | `自动对账.py:parse_output` | 用正则从文本抽 `可判定/PASS/报警`、陈旧明细、采集明细 | `自动对账.py:217-220`、`消息.py:36-89` |
| 8 | `自动对账.py:finally` | 只关本次起的那几个无头浏览器，用户开的窗口不动 | `自动对账.py:227-232`、`子流程.py:46-64` |

| 10 | `自动对账.py:build_message` / `build_sso_message` → `通知.notify` | 拼数据监控消息和登录态消息；先 webhook，失败退小助手 | `自动对账.py:257-297`、`消息.py:92-161`、`通知.py:81-93` |
| 11 | `自动对账.py:main` 收尾 | 打印 `退出码 N（...）` 和日志相对路径，恢复 stdout、关日志、返回 rc | `自动对账.py:299-309`、`日志.py:71-76` |

`每日对账.py` 的 5 个阶段（它自己的分节是 `[1/5]`…`[5/5]`，`每日对账.py:5-10`）：

| 阶段 | 入口 | 关键动作 | 失败后果 |
|---|---|---|---|
| `[1/5]` 凭证刷新 | `每日对账.py:208-220` → `凭证刷新.run` | 从浏览器读最新 cookie；失败不阻断，沿用现有 curl | 不直接改 rc，取数会暴露 |
| `[2/5]` 平台取数/契约 | `每日对账.py:222-250` → `平台取数.main`、`契约.check_platform` | 所有 `[店铺] list` 店铺 × 本月；取完立刻验 CSV 形状 | 没全成功 rc=1；契约不符 rc=6 |
| `[3/5]` 库内导出/契约 | `每日对账.py:252-324` → `库内导出.do_export/export_ingest`、`契约.check_std/check_sim/check_ingest/check_shops` | 导标准投、简单投、入库时间表；形状和店铺名逐字校验 | 导出失败 `db_ok=False`，最终 rc=4；契约不符 rc=6 |
| `[4/5]` 判定 | `每日对账.py:326-514` → `load_platform` / `load_db` / `load_ingest` / `acc_median_before` / `判定.judge` | 逐店逐日组装信号；只有 `通过/报警` 计数 | 有报警 rc=3；无一项可判 rc=4 |
| `[5/5]` 写表 | `每日对账.py:516-534` → `写入日监控.main` | 重建 `01_日数据监控.xlsx` 的「日监控」 | 写表异常且无更高优先级码时 rc=5（`每日对账.py:555-556`） |

`每日对账.py` 的退出码是在收尾处按固定顺序判的（`每日对账.py:540-557`）：`db_ok` → `库内未导` → `库内采集中` → `平台陈旧` → `judged==0` → `报警` → 写表失败。前面的码优先，例如既有报警又写表失败时返回 3 而不是 5。

## 2. 退出码全表

`RC_TEXT` 是文案表，不是所有码的“定义处”；每个码还要看 `return`（`消息.py:18-33`）。

| 码 | 含义 | 谁定的 | 人该怎么处置 |
|---:|---|---|---|
| 0 | 全部通过 | `每日对账.py:557`；`自动对账.py:309` 透传 | 无需动作；如带了 `--always-notify` 会收到一条“全部通过” |
| 1 | 取数失败（凭证或网络） | `平台取数.py:218-241` 返回 1；`每日对账.py:237-240`、`每日对账.py:331-333` | 看浏览器是否登录、`凭证状态.csv`；修好后重跑 |
| 2 | 缺少 Python 依赖 | `每日对账.py:183-184`；`自动对账.py:187-189` | 按日志里的 `pip install` 命令装包，确认用的是同一个解释器 |
| 3 | 有报警 | `每日对账.py:553-554` | 看 `报警明细`，再跑 `python 排查.py <日期>` 定位到账户/日期（`每日对账.py:499`） |
| 4 | 数据不完整（库内仍在采集 / 平台数未更新 / 库内未导） | `每日对账.py:543-552`；另 `每日对账.py:351-353` 区间为空也返回 4 | 等采集完/重取/补导后重跑；**它不是“全部通过”** |
| 5 | 写表失败 | `每日对账.py:531-534`；`每日对账.py:555-556` | 关掉占用的 Excel，单独重跑 `python 写入日监控.py`；对账结果不受影响 |
| 6 | 代码/配置契约不符（要改代码或配置，等一等不会好） | `每日对账.py:192-197`、`每日对账.py:250`、`每日对账.py:314`、`每日对账.py:324` | 按报错改适配层 CSV 或 `项目配置.ini` 的 `[店铺]`，不要反复重跑 |
| 9 | 环境没准备好（浏览器起不来） | `自动对账.py:203-206`、`自动对账.py:211-213`、`自动对账.py:223-226`；`--test-notify` 失败也复用 9（`自动对账.py:175`） | 先起代理/浏览器，或手动跑 `python 自动对账.py --force --always-notify` |

补充三点：`RC_TEXT` 里没有 7、8，这两条主链的代码里也没有对应的 `return`；未知码只会显示“未知”（`自动对账.py:220`、`自动对账.py:304`）。4 的实际范围比文案宽：除了文案列的三种，还包括库内导出失败、判定区间为空、`judged==0`（`每日对账.py:543-552`）。5 也不一定出现：`写入日监控.py` 自己会捕获 `PermissionError` 并另存 `_待替换`，只有异常越过它，`每日对账.py` 才会把 `write_ok` 置假并返回 5（`写入日监控.py:685-698`）。

## 3. 常见故障表

| 症状 | 最可能的原因 | 怎么确认 | 怎么修 |
|---|---|---|---|
| 取数 401 / 全部未登录 | 24h 会话固定约 15:05 到期；15:00~15:10 用 `--no-refresh` 会读到匿名 cookie；浏览器 profile 路径不对 | 日志出现 `cookie 已失效（401）`（`平台取数.py:121-125`）；`python 凭证刷新.py` 不是 N/N（`接新客户一页清单.md:133`）；profile 指错会“全部未登录”（`启动取数浏览器.py:55`） | 打开取数浏览器重新扫码；避开 15:00~15:10；重跑时不要 `--no-refresh` |
| ProxyError | 本机代理没起（例如 `127.0.0.1:7897`）；凌晨补跑时代理和浏览器都没起 | 日志 `ProxyError` / `取数失败`（`平台取数.py:104-120`）；看代理进程和端口 | 先起代理再重跑；凌晨补跑要先确认代理和浏览器已起，再决定是否用 `--force`（`模板/项目配置.ini:87-94`） |
| 库连不上 | MySQL 不可达、连接配置错、驱动问题 | 日志 `!! 导出失败`，`db_ok=False`，最终 rc=4（`每日对账.py:272-295`、`每日对账.py:543-544`） | 修网络/账号；临时用 `--no-db` 沿用现有 CSV，或手动导出后重跑（`每日对账.py:14`） |

## 4. 日志在哪、怎么看

| 项 | 说明 | 证据 |
|---|---|---|
| 目录 | 项目根下的 `logs/` | `路径.py:88` |
| 命名 | `YYYY-MM-DD_HHMM.log`；同一分钟重跑自动加 `_2`、`_3`，不覆盖 | `日志.py:27-40` |
| 编码 | UTF-8 带 BOM，PowerShell 5.1 的 `Get-Content` 也能直接读 | `日志.py:11-13`、`日志.py:40` |
| 写入方式 | `Tee` 同时写控制台和日志；`pythonw` 下没有控制台，不接管第一句 `print` 就会崩 | `日志.py:43-68`、`自动对账.py:133-134` |
| 子进程输出 | `run_script` 设 `PYTHONIOENCODING=utf-8`，逐行打印，Tee 负责落盘 | `子流程.py:22-35` |
| 保留 | `LOG_KEEP_DAYS=90`；`prune_logs()` 按 mtime 删除 90 天前的 `*.log`，在自动对账收尾时调用 | `日志.py:23-24`、`日志.py:79-93`、`自动对账.py:222` |
| 心跳日志 | 另写 `logs/心跳_YYYYMM.log`，每次检查追加一行 | `心跳检查.py:54-67` |

怎么看：先看最后 20 行，找 `退出码 N（...）`（`自动对账.py:304`）；再找 `结论`、`报警明细`、`平台数陈旧明细`、`库内采集中明细`（`每日对账.py:446-499`）。日志乱码时先确认用 UTF-8 读；不要用 GBK 硬解（`日志.py:11-13`）。

```powershell
Get-Content .\logs\2026-11-25_1530.log -Tail 20 -Encoding UTF8
Select-String -Path .\logs\*.log -Pattern '退出码|报警明细|平台数陈旧|库内采集中'
```

## 5. 心跳检查：S1~S4 与为什么另起任务

`心跳检查.py` 只回答一个问题：今天那次自动对账到底跑了没有、跑成了没有；四条都过才算健康（`心跳检查.py:3-17`、`心跳检查.py:177`）。

| 判据 | 含义 | 证据 |
|---|---|---|
| S1 | 今天有运行日志：`logs/YYYY-MM-DD_*.log` 存在 | `心跳检查.py:13`、`心跳检查.py:148-151` |
| S2 | 最新那份日志退出码是 0 或 4；4 表示数据没采完，属正常 | `心跳检查.py:14`、`心跳检查.py:162-163` |
| S3 | 平台取数是新的：`日汇总.csv` 的 `max(fetched_at)` 距今不超过 26 小时，且 `max(statistics_date)` 已到“今天” | `心跳检查.py:15-16`、`心跳检查.py:50`、`心跳检查.py:166-175` |
| S4 | 今天不是被时段护栏跳过：日志里没有“未运行（不在时段” | `心跳检查.py:17`、`心跳检查.py:96-98`、`心跳检查.py:155-156` |

S2 有一个宽限：日志存在但还没有“退出码”行，90 分钟内算“运行中”，超过 90 分钟才算异常；否则 16:00 撞上 15:30 那趟还没跑完就会误报（`心跳检查.py:19-20`、`心跳检查.py:157-161`）。

为什么它要跑在另一个任务里：`自动对账.py` 只在“跑起来以后”才可能推送；任务没触发、机器没开机、`pythonw` 路径变了、任务被禁用时，一条消息都不会有，表现和“一切正常”完全一样。自己检查自己，任务不触发时它也会一起死（`心跳检查.py:5-10`）。所以计划任务单独建在 16:00，比 15:30 晚 30 分钟，给 15:30 那趟留 25 分钟余量（`心跳检查.py:31-35`、`接新客户一页清单.md:168`），并且用 `python.exe` 而不是 `pythonw.exe`，出问题时能在任务历史里看到输出（`心跳检查.py:35`）。心跳自己的退出码是 0 全部健康 / 1 有异常 / 2 目标或项目目录读不到，不在上面的 `RC_TEXT` 表里（`心跳检查.py:28-29`）。

## 6. 不要做的事

1. **不要在 15:00~15:10 跑 `--no-refresh`**：24h 令牌固定每天约 15:05 到期，这个时段会读到匿名 cookie，所有店全 401（`接新客户一页清单.md:155`）。要跑就先刷新凭证。
2. **不要拿 T-1 的差额当最终结论**：按清单口径，判定对象是 T-2，T-1 只写表；T-1 的数据仍可能被后续重跑改写（`接新客户一页清单.md:156`）。看到 T-1 报警，先等下一轮重跑确认，再决定是否排查。
3. **不要只连 browser 端点读 cookie**：Edge 的 browser 级端点不认 `Network.getAllCookies`（会 `-32601`），只连它一次失败就没有第二次机会；现有实现是“browser → 各 page”×“Storage → Network”逐个试，改这块时不要退回去（`接新客户一页清单.md:160`、`凭证刷新.py:69-73`、`凭证刷新.py:130-140`）。
4. **不要把 rc=4 当成“全部通过”**：4 只表示数据不完整/无法形成可判定结论；心跳把 4 当“链路正常”，是因为它只关心任务有没有跑，不关心对账平不平（`心跳检查.py:14`、`每日对账.py:500-503`）。看到 4 仍要看日志里的“库内未导/采集中/平台陈旧”明细。
